# 視聴率分析ダッシュボード 監視Lambda（番人）

EPG・動画・AI分析結果の3系統をS3上で突合し、異常をメールで通知する。

```
EventBridge Scheduler ──15分ごと──> Lambda(mode=watch)  ① EPG存在  ② 動画到達  ③ サイズ
                      └─毎朝9:00──> Lambda(mode=daily)  ④ 分析到達  ⑤ 分析内容 + 日次サマリ
                                          │
                                          ├─> S3 (bangumi-info)   読み取りのみ
                                          ├─> DynamoDB            通知の重複抑止のみ
                                          └─> SNS                 メール通知
```

設計の中心は「異常を検知する」ではなく **「期待した正常が来ないことを検知する」**。
障害の多くはエラーを出さず沈黙する形で現れるため、番組表（EPG）を期待値マスタとして
実績と突合する。


## S3のキー規則

```
EPG    epg-all/bangumi_{放送日}.json
動画   movie/{ch}/{番組終了日}/{CH}_{番組開始日}_{HHMM}00.mp4
分析   results/{ch}/{番組終了日}/{CH}_{番組開始日}_{HHMM}00_corners.csv
```

日跨ぎ番組はフォルダ日付とファイル名の日付がズレる。

```
08/31 23:45-09/01 00:15 → movie/ch6/20260901/CH6_20260831_234500.mp4
09/01 00:15-09/01 00:20 → movie/ch6/20260901/CH6_20260901_001500.mp4
```

EPGの `EndTime` / `StartTime` からそのまま計算しているので特別扱いは不要。

### チャンネル対応（リモコンキーID）

| ch | ChannelId | 局 | 現在 |
|---|---|---|---|
| ch1 | 0x0C10 | 東海テレビ | 収録中 |
| ch4 | 0x0C28 | 中京テレビ | 収録中 |
| ch5 | 0x0C18 | CBC | 未 |
| ch6 | 0x0C20 | メ～テレ | 収録中 |
| ch10 | 0x8430 | テレビ愛知 | 未 |

5局化するときは環境変数 `CHANNELS` に `ch5,ch10` を足すだけ。コード修正は不要。

## セットアップ

**2段階に分けて進める。**

初回はキー規則の理解がズレていて未達が大量に出る可能性がある。
いきなりメールが飛ぶ状態にせず、まずS3読み取りだけで空撃ちして
出力の妥当性を確認する。

`SNS_TOPIC_ARN` が未設定なら通知は送らず CloudWatch Logs に
`[SNS未設定]` として本文がそのまま出る。DynamoDBも無ければ
例外を握り潰して素通りする（状態が読めなくても監視は止めない設計）。
つまり **フェーズ1の構成だけで実物のS3に対して検証できる。**

## フェーズ1：空撃ち検証（S3読み取りのみ）

### 1-1. IAMロール

IAM → ロール → ロールを作成 → AWSのサービス → Lambda

ロール名: `bangumiWatchdogRole`

`AWSLambdaBasicExecutionRole` を選択して作成。
作成後、インラインポリシーを追加（名前は `s3-read-bangumi` など）。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::bangumi-info",
        "arn:aws:s3:::bangumi-info/*"
      ]
    }
  ]
}
```

この段階では **S3の読み取り権限しか無い**。監視が誤って本番データを
壊すことも、意図せずメールを飛ばすこともない。

### 1-2. Lambda関数

Lambda → 関数の作成 → 一から作成

- 関数名: `bangumi-watchdog`
- ランタイム: Python 3.12
- アーキテクチャ: x86_64
- 実行ロール: 既存のロールを使用 → `bangumiWatchdogRole`

作成後、**設定 → 一般設定 → 編集**

- メモリ: 512 MB
- タイムアウト: 3分

**設定 → 環境変数**（この2つだけ）

| キー | 値 |
|---|---|
| `BUCKET` | `bangumi-info` |
| `CHANNELS` | `ch1,ch4,ch6` |

**コード → アップロード元 → .zipファイル** で
`bangumi-watchdog-lambda.zip` をアップロード。

**ランタイム設定 → 編集** でハンドラを `handler.lambda_handler` にする。
既定は `lambda_function.lambda_handler` なので必ず変更する。

### 1-3. テスト実行

テストタブ → 新しいイベントを作成

- イベント名: `watch` / イベントJSON: `{"mode": "watch"}`
- イベント名: `daily` / イベントJSON: `{"mode": "daily"}`

それぞれ保存してテスト実行する。

### 1-4. 出力の確認

CloudWatch Logs（モニタリング → CloudWatchログを表示）で以下を見る。

**watch モードの戻り値**

```
{'mode': 'watch', 'programs': 85, 'epg_problems': 0,
 'video_missing': 0, 'video_zero_size': 0, 'video_size_odd': 0, 'notified': []}
```

チェックポイント:

| 項目 | 期待 | 外れたときに疑うところ |
|---|---|---|
| `programs` | 80前後 | 0ならEPGが読めていない。バケット名・プレフィックス・IAM |
| `epg_problems` | 0 | 1以上ならログ本文に理由が出る |
| `video_missing` | 少数 | **大量ならキー規則の理解がズレている** |
| `video_size_odd` | 0〜数件 | 多いなら `VIDEO_BYTES_PER_SEC` の見直し |

`video_missing` が多い場合は、ログに出ている `s3://...` のパスを
実際のS3コンソールと1件だけ突き合わせれば、どこがズレているか分かる。

**daily モードの出力**

`[SNS未設定]` に続いて日次サマリの本文が丸ごと出る。
①〜⑤の判定結果がそのまま読めるので、内容が妥当か確認する。

### 1-5. 判断

出力が妥当ならフェーズ2へ。ズレがあれば `config.py` を直して再アップロード。

主に効く設定値:

| 設定 | 既定 | 意味 |
|---|---|---|
| `VIDEO_GRACE_MINUTES` | 30 | 番組終了から未達判定までの猶予（分） |
| `LOOKBACK_HOURS` | 36 | 未達を遡って探す範囲（時間） |
| `EPG_GAP_TOLERANCE_SEC` | 300 | EPGの時間軸ズレの許容。実データに1〜5分のズレが常時あるため無視が必要 |
| `ANALYSIS_WINDOWS` | 05:30-08:30 / 15:30-19:00 | AI分析の対象時間帯。一部でも重なれば対象 |
| `VIDEO_BYTES_PER_SEC` | 118000 | サイズ判定の基準。実測 810MB÷7194秒 |
| `VIDEO_SIZE_TOLERANCE` | 0.35 | サイズの許容乖離（±）。数日運用してから絞る |

## フェーズ2：通知の有効化

### 2-1. DynamoDBテーブル

DynamoDB → テーブルの作成

- テーブル名: `pipeline_status`
- パーティションキー: `pk`（文字列）
- ソートキー: `sk`（文字列）
- 設定: デフォルト（オンデマンド）

作成後 → 追加設定 → 有効期限(TTL) → 属性名 `ttl` を有効化。
14日で自動削除されるので手入れ不要。

用途は **通知の重複抑止だけ**。判定そのものは毎回ステートレスに計算する。
15分ごとに走るため、これが無いと同じ障害で1日96通届く。

### 2-2. SNSトピック

SNS → トピック → トピックの作成

- タイプ: スタンダード
- 名前: `bangumi-watchdog-alert`

作成後 → サブスクリプションの作成

- プロトコル: Eメール
- エンドポイント: `ykishimoto@nbn.co.jp`

**確認メールが届くので本文のリンクをクリックすること。踏むまで配信は始まらない。**
差出人は `no-reply@sns.amazonaws.com`。社内のメールフィルタで
迷惑メール判定されないか、最初の1通で確認しておく。

トピックのARNを控える。
（`arn:aws:sns:ap-northeast-1:656445866169:bangumi-watchdog-alert`）

## 動作の詳細

### watch モード（15分ごと）

**① EPGの確認**

`epg-all/bangumi_{YYYYMMDD}.json` を **今日・昨日・一昨日の3日分**読む。
EPGファイルの1日は「その日の04:30頃〜翌朝05:20頃」を収録しており、
深夜番組は前日ファイルに載るため。`(ch, 開始時刻)` で重複排除する。

見るのは **当日ファイルの存在**と **監視3局の番組が1件以上あるか** の2点。
ここが欠けると期待キューが空になり「未達ゼロ＝全部正常」に見えるため P1。

毎回読み直しているのが肝で、EPGは1日7回（04/10/13/15/18/21/23時）
上書きされるため、**特番や延長で編成が変わっても自動追従する**。
期待値を保存する設計だと編成変更のたびに誤検知が出る。

**② 動画の到達確認**

終了時刻が「今から30分以上前」かつ「36時間以内」の番組を期待キューとする。
存在確認は番組ごとの `head_object` ではなく、該当日フォルダを
`list_objects_v2` で一括取得してメモリ上で突合する。
1回の実行でLIST 6回程度で済み、サイズも同時に取れる。

**③ サイズの妥当性**

収録は H.264 1280x720 / 総ビットレート約944kbps でほぼ固定のため、
サイズが尺に比例する。`118,000バイト/秒 × 尺` と比べて ±35% を外れたら異常。

```
実測: 810MB ÷ 7194秒 = 118,000 バイト/秒
```

②のLISTで取れたサイズを使うので追加のAPI呼び出しもffmpegレイヤーも不要。
ただし閾値は実測1本から引いた暫定値なので **日次サマリのみ（P3）** とし、
即時通知はしない。数日分溜まってから `VIDEO_SIZE_TOLERANCE` を絞る。

### daily モード（毎朝9:00）

**④ 分析結果の到達**

前日の番組のうち `ANALYSIS_WINDOWS` に一部でも重なるものを対象とし、
`results/` 配下の存在を確認する。
視聴率が翌日にならないと出ないため、1次判定は設けず翌朝の1回のみ。

**⑤ 分析結果の中身**

Geminiは失敗せずにそれっぽい出力を返すことがあり、成功/失敗の二値では
捕まらない。CSVを実際に読んで妥当性を見る。

| 検査 | 狙い |
|---|---|
| 区間が隙間・重複なく連続しているか | 抜け落ちの検知 |
| 最終 `end_sec` が尺の98%以上か | 途中切れ＝`MAX_TOKENS` の検知 |
| `filename` / `channel` 列がパスと一致するか | 別番組の結果を書き込む事故の検知 |
| 行数が尺に対して十分か | 出力の劣化 |
| `segment` が既知10語彙のみか | スキーマ崩れ |
| 同一 `title` の3回以上連続 | 固着・ハルシネーションの兆候 |
| CM比率が2〜45%か | 区間分割の破綻 |

`csv_check.py` はAWS非依存なので、CSVを1本持ってくればローカルで単体テストできる。

**日次サマリ**

①〜⑤の結果を1通にまとめる。**異常が無い日も必ず送る。**
届かない日は監視Lambda自体が止まっているということで、監視の監視を兼ねる。

## 通知の設計

| レベル | 内容 | 通知 |
|---|---|---|
| P1 | EPG不在 / 2局以上が同時に動画未達 | 即時メール |
| P2 | 1局のみの動画未達 / 分析の未達・内容異常 | 即時メール |
| P3 | EPGの時間軸ズレ / 動画サイズの乖離 | 日次サマリのみ |

未達は **局ごとにまとめて1通**にする。収録PCが落ちると数十番組が
一斉に未達になるため、番組ごとに送ると1回の障害で数十通飛び、
すぐ誰も読まなくなる。

未達の局数で重要度を切り替える。

- 2局以上 → P1「収録PC本体・アップロード処理・回線の障害の可能性が高い」
- 1局のみ → P2「チューナーまたはその番組固有の問題の可能性が高い」

SNSのSubjectは **ASCII・100文字未満**という制約があるため、
件名は英数字、日本語は本文に入れている。

本文には「何が起きたか」だけでなく **次に何を見ればいいか** まで書く。

```
件名: [P1] Video missing: 3 ch (2026-08-31 09:00 JST)

【P1】動画がS3に上がっていません（2026-08-31 09:00 JST）

■ ch1(東海テレビ) … 1件
    04:55-05:25 めざましテレビ全部見せ
      s3://bangumi-info/movie/ch1/20260831/CH1_20260831_045500.mp4
■ ch6(メ～テレ) … 3件
    ...

正常だった局: なし

判定: 複数局が同時に未達です。個別のチューナーではなく、
収録PC本体・アップロード処理・回線の障害である可能性が高いです。

確認先:
  1. 収録PCのログ（収録が失敗したのか、アップロードが失敗したのか）
  2. 収録PCのディスク空き容量
  3. 収録プロセスの生存
```

## 未実装・今後

**画音の品質検査（③の残り）**

`blackdetect` / `silencedetect` / `freezedetect` は未実装。
2時間810MBならLambdaの `/tmp`（10GB）に収まるので、
ffmpegのLambda Layerを追加すれば同じ関数に組み込める。
先頭・中間・末尾の各30秒サンプリングで実用になる。

**収録PCのディスク空き容量**

収録は生放送なので失敗すると取り返しがつかず、停止原因で最も多いのが
ディスク満杯。これは唯一「事前に分かる」故障だが、S3不在検知は
起きてから気づく仕組みなので拾えない。

収録PC側でタスクスケジューラから日次1回、空き容量をメール送信するだけの
スクリプトを別途用意するのが有効。監視の仕組み自体は不要。

**視聴率データ・天気データ**

現状は監視対象外。ダッシュボードの入力としては同格なので、
`results/` と同じ要領で到達チェックを足せる。
